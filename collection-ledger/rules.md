# rules

このプロジェクトの定款。作業前に必ず読む。

## 禁止事項

- 外部ライブラリを勝手に追加しない。
- 確認済みの指示範囲から外れて、ついで実装・将来対策・安全策を勝手に実行しない。
- DBの破壊的変更をしない。
  - `drop`
  - `truncate`
  - 既存カラム削除
  - 未確認の一括上書き
- 既存プロジェクト `C:\Users\toyoaki\Desktop\filedatachange` を明示指示なしに変更しない。
- 重複候補ファイルを自動削除しない。
- ブラウザAPIと実処理ジョブを同じ場所に混ぜない。
- ルート直下に野良の実行JSを増やさない。
- あいまいなまま推論で決定しない。危険な分岐は2案以上を提示して確認する。

## 確認と実行のルール

- ユーザーの指示は最優先であり、エージェントが勝手に言い換えたり、形式を崩したりしない。
- 指示を拡大解釈する必要がある場合、または複数の解釈があり得る場合は、実行前に必ずユーザーへ確認する。
- ユーザーの指示、仕様書、設計書、MD、runbookは提案資料ではなく作業命令として扱う。
- 仕様書に書かれていることだけを実行する。仕様書に書かれていないことは、ユーザーが漏らした・不足している・検証していないと推測しない。
- 仕様書にない機能追加、便利化、安全策、将来対策、別方式への置き換えは、実装せずに必ず先に確認する。
- ユーザーが明示していないことを、善意や効率化のつもりで補完しない。
- 「ユーザーがあほだから漏れているだろう」という前提に立たない。漏れに見えるものは、不要だから書かれていない可能性を第一に扱う。
- 仕様書にないが必要に見える項目は、作業対象ではなく質問事項として扱う。
- 判断するのはユーザー。エージェントは提案してもよいが、ユーザーのOKなしに実行しない。
- 復唱した場合は、復唱した内容だけを実行する。復唱に含まれない作業は実行しない。
- 「ついでに」「今後のために」「安全そうだから」と思った内容は、実装前に提案として出す。
- DB変更、SQL変更、削除、移動、運用ルール変更は特に必ず事前確認する。
- ユーザーが「止まって」「動くな」「確認」と言った場合は、作業を停止し、確認・報告だけに切り替える。

## 仕様書ベース作業の必須手順

仕様書、設計書、MD、runbook、質問回答、チェックリスト、既存運用メモを前提にする作業では、次の手順を必ず実施する。

- 読むタイミング:
  - 作業開始時に `rules.md` を読んだ直後、対象仕様書を読む。
  - 実装、DB変更、ファイル移動、バッチ配置、運用配置、本実行の直前に、対象仕様書の該当箇所へ戻って読む。
  - 最終報告の直前に、対象仕様書の完了条件へ戻って読む。
- 実装前に、仕様書から完了条件チェックリストを作る。
  - 実装コード。
  - DB、SQL、view、seed、権限。
  - ファイル配置。
  - NAS、外部ドライブ、運用フォルダ配置。
  - バッチ配置。
  - dry-run、本実行、CSV、ログ。
  - ブラウザ表示、API、実ファイル起動。
  - 未処理、未確定、手動確認CSV。
- チェックリストは「読んだ」では完了にしない。実パス、件数、コマンド結果、API結果、ブラウザ確認など、確認できた事実で完了にする。
- リポジトリ内の実装場所と、実運用上の配置場所を分けて確認する。
  - 例: `ops/batches` にあるだけでは、NAS上の `?:\uncen\...\*.bat` 配置完了とは扱わない。
- 「完走」「完了」と言う前に、仕様書の各完了条件と実状態を1対1で照合する。
- 照合できていない項目は、未完了または未確認として報告する。曖昧なまま完了扱いにしない。
- 仕様書と実装・運用配置が矛盾する場合は、実行を止めてユーザーに確認する。

## 既存踏襲タスクの必須手順

- ユーザーが「踏襲」「既存と同じ」「前と同じ」と言った場合、実装前に必ず既存実装・既存運用を確認する。
- 既存方式を短く報告してから、同じ方式で進める。
- 既存確認が終わるまで、一般解や別方式を採用しない。
- 既存と違う方式を使いたい場合は、理由を添えて提案し、ユーザーのOKを待つ。
- 目的が同じでも方式が違う場合は、指示外として扱う。

## 優先事項

- ローカル完結を優先する。
- 既存プロジェクトの使い勝手と運用知見を尊重する。
- 既存の肥大化から学び、責務を最初から分離する。
- 手動実行とPM2自動実行で同じjob入口を使う。
- dry-run、ログ、run id、CSV出力、エラー追跡を重視する。

## DBルール

- PostgreSQLを使う。
- 新規DBオブジェクトは専用schema `cl` に作る。
- DBオブジェクト名はすべて小文字にする。
- schema、table、view、column、index、sequenceの名前は小文字。
- `public` と既存 `xxx_...` 系の資産とは混ぜない。
- `bigserial`、`serial`、identityを使う場合はsequence権限付与を忘れない。
- schema権限、table権限、sequence権限、default privilegesを設計に含める。

## 実装ルール

- `apps/web`: ブラウザUI。
- `apps/api`: ブラウザUI専用API。
- `apps/jobs`: 手動実行・PM2自動実行の入口。
- `packages/*`: 共通部品、ドメイン、DB、スクレイピング、サイト固有処理。
- 手動実行は `node apps/jobs/xxx.js` を正式な運用として許容する。
- npm scriptsはショートカットであり、必須の入口にはしない。
