# Site Expansion Runbook

Manual thumbnail and per-NAS owned-file batch operations are documented in
[`manual-batch-operations.md`](manual-batch-operations.md).

この文書は、PACOで確立した進め方を、次のサイト追加時に再現するための手順書。

目的は、次のプロジェクト名、DB取得先サイトアドレス、サムネイル取得先、実ファイルの集め方などを質問票で確認し、回答後にマスター、所持、DL参照、ブラウザ表示、本運用バッチまで順番に実装できる状態にすること。

## 0. 最初に読むMD

作業開始時は、必ず次の順で読む。

1. `rules.md`
   - 作業範囲、確認、禁止事項、DBルール、既存踏襲ルールを確認する。
2. `AGENTS.md`
   - エージェント作業時の最優先ルール、レビュー運用、停止指示の扱いを確認する。
3. `docs/decisions.md`
   - プロジェクト名、技術構成、DB schema、レイヤー分離の決定事項を確認する。
4. `docs/design.md`
   - `apps/web`、`apps/api`、`apps/jobs`、`packages/*`、`ops` の責務を確認する。
5. `docs/common-db-outline.md`
   - raw、staging、正式、CSV確認、所持、view までの共通DB外郭を確認する。
6. `docs/site-master-registration-workflow.md`
   - PACOで確立したマスター、所持、DL参照、サムネイル、ブラウザ前提を確認する。
7. `docs/paco-owned-file-design.md`
   - 所持ファイル本体テーブルと出演者リンクテーブルの2テーブル構成を確認する。
8. `docs/reusable-parts.md`
   - 既存から踏襲する部品、変える点を確認する。
9. `docs/new-rules.md`
   - DB、ディレクトリ、job、レビューの短縮ルールを確認する。
10. `ops/pm2/README.md`
    - PM2から起動する場合も `apps/jobs/*.js` と同じ入口を使うことを確認する。

次にブラウザUIを作る場合は、既存プロジェクト `C:\Users\toyoaki\Desktop\filedatachange` のUIとAPIも読み、踏襲する方式を短く報告してから進める。

## 1. 絶対ルール

- 判断者はユーザー。
- 相談段階では作成、編集、実行をしない。
- 復唱した場合は、復唱した範囲だけ実行する。
- 指示外の「ついで」「今後のため」「安全そうだから」は実装しない。
- 指示外の改善をしたい場合は、先に提案し、明示OKを待つ。
- DB変更、SQL変更、削除、移動、運用ルール変更は事前確認する。
- 「止まって」「動くな」「確認」と言われたら作業を止め、報告だけにする。
- 「踏襲」「既存と同じ」と言われたら、先に既存実装と既存運用を確認して報告する。
- ブラウザUI/APIと、実処理job JSを混ぜない。
- 実処理入口は `apps/jobs` に置く。
- DBは `cl` schema、小文字名、sequence権限まで見る。
- 本実行前に必ずdry-run、CSV/JSON、レビュー、人間確認を挟む。
- ファイル移動、リネームは上書き禁止。
- trash行きは原則リネームしない。

## 2. 最初の質問票

新しいサイトを追加する時は、まず以下を2件ずつ質問する。
ユーザーが混乱しないよう、一気に全部聞かない。

### Q1. サイト識別

- `source` 名は何にするか。
- 表示名、正式サイト名は何か。
- マスター番号は何番にするか。例: `m001`
- `source` 名と違うDB接頭語が必要か。

なぜ聞くか:

- DB名、ディレクトリ名、job引数、UIタブ名、view名の基準になるため。
- PostgreSQLでは小文字名を使うため、最初に表記を固定する必要がある。

固定ルール:

- DB接頭語は原則として `source` 名を使う。
- マスターは `cl.{source}_{master_no}_...` の形を基本にする。
- `source` と違うDB接頭語を使いたい場合だけ、理由を確認する。

### Q2. マスター取得元

- 一覧URLは何か。
- ページング方式は何か。
- 1ページ件数は何件か。
- ユーザー想定の最大ページ数は何ページか。
- 詳細ページを見る必要があるか。

なぜ聞くか:

- スクレイピング範囲、ランダムウェイト、全件取得件数、dry-run件数を決めるため。

固定ルール:

- 最大ページ数はユーザー想定を聞いた後、実HTML確認時に再確認する。

### Q3. 一意キー候補

- サイト側で1意になりそうな値は何か。
- 所持ファイル名に含まれそうな値は何か。
- サイト側と所持側で表記揺れがあるか。

なぜ聞くか:

- PACOでは日付が1意ではなく `movie_code` が正解だった。
- ここを誤るとマスターも所持照合も崩れるため。

### Q4. 取得カラム

- 一覧から取る項目は何か。
- 詳細ページから取る項目は何か。
- タイトル、出演者、公開日、URL、サムネイルURLは取れるか。
- rawとして残したい値は何か。

なぜ聞くか:

- raw/staging/正式テーブルのカラム設計に直結するため。

### Q5. サムネイル

- サムネイルURLはどこから取れるか。
- 一覧で取れるか、詳細で取る必要があるか。

なぜ聞くか:

- ブラウザ表示の主要情報になるため。
- 自動取得できるかどうかで、ジョブ設計と手動補完の扱いが変わるため。

固定ルール:

- 保存名は原則として一意キー名にする。
- 自動取得分と手動補完分は、最終的に本流のサムネイルディレクトリへ合流する。
- 自動取得できないものは手動補完候補として分け、必要性判断は実データ確認後に行う。

### Q6. 所持ファイル収集

- 検索語は何か。

なぜ聞くか:

- 対象ファイルを探すためのサイト固有キーワードだけは毎回変わるため。
- それ以外の収集ルールはPACOで汎用ルールとして固定したため。

固定ルール:

- 対象はPACOと同じく全NAS。
- ストレージ間移動は禁止。
- 各NAS内だけで移動する。
- 収集段階では検索語に一致するファイルを広く集める。
- 照合、登録対象は `.mp4`、`.mkv`、`.avi` など動画拡張子全般にする。
- 既存ファイルは各NAS直下の `\uncen` フォルダ内へ集める。
- 集約先は `source` 名のフォルダにする。

例:

```text
N:\uncen\{source}
K:\uncen\{source}
```

### Q7. 小規模手動バッチ運用

- PM2自動実行も同時に必要か。

なぜ聞くか:

- 小規模サイトでは手動バッチ運用を基本にするため。
- PM2自動実行が必要な場合だけ、追加で運用設計するため。

固定ルール:

- 小規模サイトは手動バッチ運用を基本にする。
- 手動バッチ運用の場合、ディレクトリ名は次の標準形にする。

```text
P:\uncen\{site_key}_new_master
P:\uncen\{site_key}_new_mp4
P:\uncen\{site_key}_trash
P:\uncen\{site_key}
```

- 次サイト以降は、ディレクトリ作成から実施する。

### Q8. DL参照

- DL可能リンクを探す検索元はどこか。
- 検索キーワードは何か。
- 最大ページ数は何ページか。
- 一覧にリンクがあるか、詳細ページが必要か。

なぜ聞くか:

- 未所持でも取得可能なリンクをブラウザで開くため。
- 一覧取得と詳細取得で処理が分岐するため。

固定ルール:

- 人がクリックするURLとhref側URLは両方保存する。
- ページ移動、詳細ページ移動には2から5秒のランダムウェイトを入れる。

### Q9. ブラウザ表示

- UI上のサイト表示名は何にするか。
- タブ名、サイドバー名は何にするか。
- サイト固有で追加したい表示列や絞り込みはあるか。

なぜ聞くか:

- 表示名、タブ名、サイト固有列だけはサイト追加ごとに変わるため。
- それ以外のUI構成と操作はPACOで汎用ルールとして固定したため。

固定ルール:

- 既存UIを踏襲する。
- 既存UIの確認を先に行い、踏襲する方式を短く報告してから実装する。
- デフォルトは `Local Library` 相当の所持一覧ページにする。
- 左タブ側には `Completion` 相当の全件/所持/未所持/DL可能の一覧を用意する。
- 所持リスト、コンプリート一覧、未所持一覧、DL可能表示を扱える構成にする。
- 動画ファイルを開く、フォルダを開く、外部リンクを開く操作を実装する。
- これらの操作はAPIだけでなく、実際にブラウザから動作確認する。
- HD/4Kなど動画メタデータによる絞り込みに対応できるDB/API/UIにする。
- BE/FEはPM2で常駐し、Windows自動起動は既存の `pm2-windows-startup` と `pm2 save` を踏襲する。

## 3. 実装順

次サイト追加では、以下の順で進める。
順番を飛ばさない。

### Phase 1. 設計とディレクトリ

1. `rules.md` と関連MDを読む。
2. 質問票 Q1-Q9 を2件ずつ確認する。
3. 共通部分とサイト個別部分を分ける。
4. `site_key` を決める。
5. 必要なら小規模バッチ用ディレクトリを作る。

補足:

- Q9はBrowser着手前に最終確認してもよい。
- DB案やサイト固有ルールは、実装前に該当docsへ反映して人間確認する。

小規模バッチ用の標準形:

```text
P:\uncen\{site_key}_new_master
P:\uncen\{site_key}_new_mp4
P:\uncen\{site_key}_trash
P:\uncen\{site_key}
```

### Phase 2. マスター取得

1. 対象HTMLを読む。
2. 1ページだけ取得して、実HTMLの構造を見る。
3. 取れるカラムを整理する。
4. 一意キー候補を決める。
5. 重複確認を行う。
6. DBテーブル案を作る。
7. DB案をdocsへ反映する。
8. 人間確認を受ける。
9. DBレビューを通す。
10. JSレビューを通す。
11. `init-db` を作る。
12. 10件程度のドライランを行う。
13. DB投入テストを行う。
14. statusで件数確認する。
15. 問題がなければ全件取得する。

PACOでの実例:

- テーブル接頭語は `paco_m001_`。
- 一意キーは `movie_code`。
- `relation_key_mmddyy` は候補キーとして保持するが、一意にはしない。
- 同じ日付の複数レコードは全部保持する。

次サイトでは、Q1とQ3の回答で置き換える。

raw/staging/正式の扱い:

- raw/staging/正式の段階を持つ。
- ただし、サイトによっては staging を人間確認済みの正式マスターとして扱う。
- 正式テーブルを別に作るかはDBレビューで決める。

### Phase 3. サムネイル

1. マスターDBにサムネイルURLを保存する。
2. 自動取得ジョブを作る。
3. DBレビュー、JSレビューを通す。
4. 1枚で取得テストする。
5. limit付きで小さく取得する。
6. 全件取得する。
7. statusで件数確認する。
8. 手動補完分がある場合は、本流ディレクトリへ合流する。

標準保存先:

```text
storage/thumbnails/{site_key}/master
```

ファイル名は原則として一意キー名にする。

### Phase 4. 共通マスター設計と初期反映

サイト別マスターができたら、次の共通マスターへ反映する。

```text
cl.site_master
cl.actor_group_master
cl.actor_name_master
```

目的:

- サイトをID化する。
- 出演者物理名をサイト単位で持つ。
- 将来、同一人物グループをまとめられるようにする。

補足:

- 初期反映後も、Phase 7でマスター補完が発生した場合は補完分を再反映する。

### Phase 5. 所持ファイル収集

1. 検索語を確認する。
2. 全NASの `\uncen` 配下に `{source}` フォルダを作る。
3. 全NASから検索語に一致するファイルを探す。
4. 収集だけのジョブを作る。
5. dry-runする。
6. 人間確認後に実移動する。

この段階では以下をしない。

- リネームしない。
- 所持DBへ正式登録しない。
- マスターと照合して勝手に整理しない。

### Phase 6. 所持照合

1. 対象フォルダをスキャンする。
2. ファイル名からキー候補を抽出する。
3. マスターDBに存在するか確認する。
4. 既に所持DBにあるか確認する。
5. CSV/JSONを出す。
6. 読取不可、マスター未登録、既存所持、移動可能を分ける。
7. 人がCSVを確認する。

この段階ではまだ正規移動、リネーム、DB登録をしない。

補足:

- 所持DBが既に存在する場合は既存所持も確認する。
- 初回構築で所持DBがまだない場合は、既存所持確認は省略または空扱いにする。
- 原則としてDB登録、リネーム、正規移動はしない。
- 人間確認後、未一致隔離だけを `unmatched` へ移動することはできる。

### Phase 7. マスター未登録補完

1. マスターにない所持ファイルをCSV化する。
2. 人がタイトル、出演者、サムネイルを調べる。
3. 不要行や重複行を人が削除する。
4. DBレビュー後、マスターへ追加する。
5. 手動サムネイルを本流へ合流する。
6. 共通マスターへ補完分を再反映する。

### Phase 8. リネームと所持正式登録

正式マスターと照合できる状態になってから実施する。

標準リネーム規則:

```text
{unique_key}_{title}_{actor}.{ext}
```

PACO例:

```text
042826_100_儚げな美熟女をとことんヤリまくる_須藤杏奈.mp4
```

所持DBは2テーブル構成を基本にする。

```text
cl.{site_key}_owned_file
cl.{site_key}_owned_file_actor
```

ルール:

- 正式命名規則はサイトごとに人間確認する。
- `{unique_key}_{title}_{actor}.{ext}` は候補として扱う。
- dry-runを必ず行う。
- 前名、新名、元パス、移動先、run id が分かるJSON/CSVを作る。
- 上書きしない。
- 照合できた動画だけリネームして正規所持フォルダへ移動する。
- trash行きは元ファイル名のまま移動する。
- DB登録は正式移動後の実パスで行う。

### Phase 8.5. 動画メタデータ

HD/4Kなど動画メタデータで絞り込みやソートを行う場合は、Browser DB/Viewの前に実施する。

1. 所持DB登録後に動画メタデータテーブルを作る。
2. DBレビュー、JSレビューを通す。
3. 小さくprobeする。
4. 全件probeする。
5. statusで件数、失敗件数、HD/4K分類を確認する。

標準形:

```text
cl.{site_key}_owned_file_video_metadata
```

### Phase 9. DL参照

1. 検索元サイトを確認する。
2. 検索キーワードを確認する。
3. 1ページだけdry-runする。
4. 一覧にリンクがあるか確認する。
5. 必要なら詳細ページ分岐を入れる。
6. 2から5秒のランダムウェイトを入れる。
7. DBレビュー、JSレビューを通す。
8. 全件取得する。
9. 混入、RGなし、マスター未登録を確認する。

DL参照は、Phase 10 Browser DB/View の前までに完了していること。

保存するURL:

- 人が開くための表示URL。
- href側URL。

### Phase 10. Browser DB/View

ブラウザAPIに進む前に、DB/Viewを揃える。

必要な状態:

- サイト別マスターが完成している。
- サムネイル参照先が整理済み。
- 共通出演者マスターが作成済み。
- 所持正式テーブルが作成済み。
- 所持とマスターのリレーションが取れている。
- 所持一覧Viewがある。
- マスター全件Completion Viewがある。
- 非所持、DL可能はCompletion Viewの条件抽出でもよい。
- 必要なら非所持View、DL可能Viewを追加する。
- 動画メタデータが必要ならHD/4K判定列がある。

### Phase 11. API / Web

ここで初めてブラウザへ進む。

1. 既存UIを確認する。
2. 既存の開き方、ファイル/フォルダ/APIの方法を確認する。
3. 既存方式を短く報告する。
4. サイト固有の表示名、タブ名、追加列だけ確認する。
5. APIを作る。
6. Webを作る。
7. 実際にブラウザで開いて確認する。
8. 動画を開く、フォルダを開く、リンクを開く動作を実確認する。
9. PM2運用に載せる。

PM2のWindows自動起動は既存方式を踏襲する。

- `pm2-windows-startup`
- `pm2 save`
- 手作りスタートアップcmdを勝手に作らない。

### Phase 12. 手動バッチ

小規模サイトでは、最終的に次の2種類を作る。

```text
P:\uncen\{site_key}_new_master\{site_key}_master_apply.bat
P:\uncen\{site_key}_new_mp4\{site_key}_owned_apply.bat
```

マスター更新バッチ:

- 最新ページを読む。
- 既存マスターとの差分だけ登録する。
- 共通マスターへ反映する。
- サムネイルを取得する。

所持登録バッチ:

- `{site_key}_new_mp4` 配下を全階層スキャンする。
- 照合できた動画だけリネームして `{site_key}` へ移動する。
- 所持DBへ登録する。
- 読取不可、マスターなし、不要候補はCSV/JSON化する。
- 人間確認済みの読取不可、マスターなし、不要ファイルだけ `{site_key}_trash` へ移動する。
- trash行きはリネームしない。

バッチ運用の安全ルール:

- 本実行バッチを作る前に、同じ処理のdry-runを必ず実行する。
- dry-run結果のCSV/JSONを人間が確認してからapplyする。
- apply対象は照合済み、人間確認済みのものだけにする。
- trash移動も人間確認済みの行だけにする。

## 4. レビューを入れる場所

DBレビューが必要な場面:

- 新規SQL。
- テーブル、view、index、sequence。
- DB投入処理。
- 既存DBへの追加、更新、削除。
- マスター未登録補完。

JSレビューが必要な場面:

- スクレイピング。
- ファイル移動。
- リネーム。
- バッチ本実行。
- APIからファイルやフォルダを開く処理。

全体レビューが必要な場面:

- レイヤー責務。
- ディレクトリ構造。
- 運用ルール。
- PM2設定。
- UI/API/jobの分離。

## 5. 実装後の確認

各Phaseの最後に確認する。

マスター:

- 取得件数。
- raw件数。
- staging件数。
- 重複キー。
- 新規差分。

サムネイル:

- URLあり件数。
- collected件数。
- failed件数。
- 手動補完件数。
- ブラウザで表示できるか。

所持:

- スキャン件数。
- 照合可能件数。
- 既存所持件数。
- マスターなし件数。
- 読取不可件数。
- 移動後の残ファイル。
- DB所持件数。

DL参照:

- 取得件数。
- リンクあり件数。
- リンクなし件数。
- 混入件数。
- マスター未登録件数。

ブラウザ:

- 一覧表示。
- サムネイル表示。
- 検索。
- ソート。
- 所持/未所持/DL可能の表示。
- 動画を開く。
- フォルダを開く。
- 外部リンクを開く。

## 6. 完了条件

次サイトの第1弾完了条件は以下。

- マスターがDB登録済み。
- サムネイルが本流へ保存済み。
- `site_master`、`actor_group_master`、`actor_name_master` へ反映済み。
- 所持ファイルが正式フォルダへリネーム移動済み。
- 所持DBに登録済み。
- DL参照DBが作成済み。
- ブラウザで確認できる。
- 手動本運用バッチが作成済み。
- dry-run / apply のCSV/JSONログが残っている。
- 今回決めたサイト固有ルールがdocsに追記されている。
